# 流量/图像压缩策略（2026 现状与落地说明）

> 本文档回答：贴吧第三方客户端在"不触发百度风控"前提下，2026 年如何尽可能压缩
> 信息传输资源、并保证缩略图与点开大图的质量。

## 1. 现实约束（为什么不能"上 2026 最牛压缩算法"）

- **贴吧 CDN 只提供服务端预先算好的若干档图**：`originPic`(原图，数 MB) /
  `bigPic`(~960px) / `srcPic`(更小档，仅部分资源提供)。**客户端注入 `w=480xH` 尺寸
  段已被停用**（2026-08 实测：一律返回默认「贴」占位图），因此"客户端自定义任意
  尺寸压缩"这条路不可行。
- **不能改 sign/接口签名**：任何对请求参数（数量、顺序、额外字段）的改动都可能
  触发百度风控。所以压缩只能做在"选哪一档 + 显示/缓存策略"，不能做在"请求怎么发"。
- 传输压缩（Brotli / gzip）由平台层（iOS URLSession / HTTP/2）自动协商，客户端
  无法也不应干预；多种 `Accept-Encoding` 头的人为修改属于可被风控识别的异常。

## 2. 落地策略（已实现/已接入）

### 2.1 大图清晰度可调（设置 → 通用 → 大图清晰度）
把"查看器加载哪一档图"作为用户可选项 `dataSaverMode`：

| 档位 | 取图 | 流量 | 适用 |
|------|------|------|------|
| 原图 | `originSrc`(originPic) | 数 MB/张 | 追求画质、Wi-Fi |
| 高清（默认） | `src`(bigPic ~960px) | 省 60-80% | 手机屏观感几乎无差 |
| 省流 | `smallSrc`(srcPic，缺失回落 bigPic) | 最省 | 流量紧张 |

- 实现：`pickViewerImages(images, mode)` 统一入口，接入
  TweetCard（信息流）/ PostContent（帖内）/ PostCard 楼中楼图片条。
- 默认 **high**：不开启任何设置也默认省 60-80% 流量，同时画质达标（满足
  "不开启时也尽量压缩但保证质量"）。
- 列表/帖内缩略图仍走服务端中等图（`src`/THUMB 档），不加载原图。

### 2.2 渲染与缓存侧（不省 CDN 流量但省内存/电）
- 查看器 `buildPageWindow`：只 decode 当前页原图，邻近页用 360px 缩略图占位，
  滑到跟前再换大图；低功耗模式窗口进一步收窄。
- expo-image `recyclingKey` + memory-disk 缓存：同 URL 不重复下载。
- 图片仅在"点进查看器"时才按所选档位加载，feed 永不大图。
- 动图/长图在卡片用 contain + 徽标，避免超长图整页下载渲染。

### 2.3 图像格式说明
- 服务端若下发 WebP/AVIF，expo-image 直接解码（无需重编码，不耗电）。
- 客户端不做二次重编码（会丢画质且耗电，违背"保证质量"目标）。

## 3. 后台签到不阻塞网络（已确认）

- 签到是**串行逐吧**（虚拟验证 200ms/吧），期间用 `setTimeout` 等待，不占任何
  全局锁；其他网络请求（看帖/看吧/动态）在 JS 事件循环中正常并行。
- 进度通知/灵动岛更新改为 `void ... .catch()`（不 `await`），避免 ActivityKit
  IPC 慢操作拖慢签到本身（且 SIGN 与实际请求互不阻塞）。

## 4. 监控/后续（可选）
- 若日后 CDN 恢复"客户端可控尺寸"，可在此框架上直接加任意档位（picker 已三档，
  加档即加一个 Picker 项）。
- 若需最激进省流：可加"图片仅 Wi-Fi 加载原图"等策略，挂在现有偏好体系上即可。
